The Ed-Fi Alliance is pleased to announce the release of **Ed-Fi ODS Admin API v2.4**. This release introduces a new `v3` API mode, lets an application hold more than one set of credentials, provisions database instances as background jobs, and adds audit logging across the operations that change configuration. It also moves Admin API to .NET 10 and removes external identity provider support.

<!-- truncate -->

## Highlights

### A new v3 API mode

Admin API v2.4 adds a `v3` mode that implements the Management API v3
specification — the same specification implemented by the Ed-Fi Configuration
Management Service, which serves the Ed-Fi API v8 platform. Admin API continues
to administer the Ed-Fi ODS / API; it does not manage an Ed-Fi API v8 instance.

The existing `v1` and `v2` surfaces continue to work as before. `v3` is
additive, and it is where the new resource model and conventions live:

- `odsInstances` is modeled as `dataStores`.
- Errors are returned as [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)
  Problem Details, served as `application/problem+json` with `errors`,
  `validationErrors` and `correlationId` extension members.
- `Location` headers carry an absolute URI.
- Claim set payloads use a flat structure.

Because `v3` defines its own conventions, clients moving from `v2` should plan
for the renames and response shapes listed under
[Before You Upgrade](#before-you-upgrade).

### Multiple credentials per application

Previously an application was effectively one-to-one with a credential. In
v2.4 an application can hold several API clients, each with its own credential,
so a vendor integration can rotate or segment credentials without creating a
second application.

Two consequences are worth noting. Editing an application no longer accepts
`enabled` or `dataStoreIds`, because those are per-client concerns. And
resetting credentials at the application level now returns `409 Conflict` when
an application has no clients or more than one — reset an individual credential
with `PUT /v3/apiClients/{id}/reset-credential` instead.

### Database instance provisioning as background jobs

Creating and deleting a database instance from a database template now runs as a
background job rather than blocking the request. Create and delete operations on
`/v3/dataStores/manage` return a `jobId`, and new endpoints report the status of
that job.

A new `EnableDataStoreManagement` feature flag turns the instance-management
endpoints and their background jobs off entirely, in both v2 and v3, for
deployments that provision databases by other means.

### Audit logging

Audit logging now covers operations that previously went unlogged. Entries
capture tenant context and the response status code, and a delete records the
natural key of the object that was removed, so an audit trail remains
interpretable after the row is gone. Audit logging applies to the v2 and v3 API
modes.

### Education organization endpoints

Education organization management has been consolidated. The deprecated
list-by-instance and list-by-data-store endpoints have been removed in favor of
the current endpoints, which now include `dbInstanceId`, and
`RefreshEducationOrganizations` returns `202 Accepted` to reflect that the
refresh runs asynchronously.

## Before You Upgrade

This release contains breaking changes. Review these before upgrading.

- **.NET 10 required.** Admin API and its supporting images target .NET 10.
  Install the [.NET 10 runtime](https://dotnet.microsoft.com/en-us/download/dotnet/10.0)
  on application hosts before upgrading. .NET 8 is no longer supported.
- **External identity provider support removed.** Keycloak-based authentication
  is gone, along with the `*-idp-*` Docker Compose files, the `env-idp.example`
  templates and the related installer options. There is no in-place upgrade
  path; deployments using an external IdP must move to the built-in
  authentication first.
- **Endpoint renames.** `apiclients` is now `apiClients` in both v2 and v3.
  In v3, `odsInstances` is `dataStores`, and instance-management routes moved to
  `/v3/dataStores/manage` and `/v2/odsInstances/manage`.
- **Removed endpoints and fields.** `/dataStores/edOrgs` and
  `/odsInstances/edOrgs` are removed in both v2 and v3, as are the deprecated
  education organization list endpoints. The `UseSandbox` and `SandboxType`
  fields are gone from the API clients resource, and `key` is now `clientId`.
- **Error payloads changed in v3.** Clients that parse the previous error shape
  must handle RFC 9457 Problem Details. The problem type URN namespace changed
  from `urn:ed-fi:admin-api:` to `urn:ed-fi:management-api:`. The v1 and v2
  error middleware is unchanged.
- **Unrecognized fields are rejected.** `PUT /v3/applications/{id}` returns
  `400 Bad Request` for an unmapped property instead of ignoring it.
- **Connection strings are no longer returned.** Data store derivative
  connection strings are encrypted at rest and omitted from API responses. Read
  them from configuration instead.
- **Data store names are capped at 46 characters** when creating a data store or
  ODS instance, in both v2 and v3, so that the generated database name fits the
  63-character portable limit. Existing records are not re-validated.

The [release notes](https://github.com/Ed-Fi-Alliance-OSS/ODS-Admin-API/releases/tag/v2.4.0)
list every change in this release, including the dependency updates.
